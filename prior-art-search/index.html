선행기술조사 — 검색식 제안에서 최근접 선행문헌 추출까지

선행기술조사는 ‘검색식을 잘 짜는 일’에서 끝나지 않습니다. 여러 DB를 같은 기준으로 뒤지고, 나온 문헌을 청구항 특징과 대비해 가장 유사하거나 가장 적은 수정으로 도달할 수 있는 문헌(최근접 선행기술)을 골라야 합니다. 이 편은 청구항에서 하나의 개념 조사식을 만들어 DB별 검색식으로 자동 변환하고, 구성대비 결과를 공개된 규칙으로 산정해 주인용·보조 문헌을 추리는 파이프라인을, 직접 돌려 본 두 도구와 함께 초보자도 따라 하기 쉽게 설명합니다.

독자선행기술·무효자료 조사를 AI로 체계화하려는 변리사·특허 실무자, 조사 입문자 분량읽기 약 25분 · 템플릿(검색식 변환 도구 · 최근접 산정 도구 · 조사 스킬 · 프롬프트 5종 · 시범 데이터) 판1.0 · 2026. 11. 9.
한 줄 결론

개념 조사식 하나를 만들어 DB별로 자동 변환하고, ‘판단’은 근거와 함께 적고 ‘순위’는 공개된 규칙으로 계산하세요 — 그래야 재현·검토가 됩니다.

AI가 “이게 제일 비슷하다”고 한 번에 결론 내리면 근거를 검증할 수 없습니다. 그래서 특징별 개시 여부(●/◐/○)를 근거 위치와 함께 기록하고, 순위는 점수 규칙으로 집계합니다. 검색은 공식 API만 자동이고, 웹 DB는 약관상 사람이 실행합니다.

무엇을 확인했나 — 검색식 변환 도구(시험 6개)·최근접 산정 도구(시험 7개)를 직접 만들어 돌렸고(5·6장 시범), 산정 결과는 참조 설계의 예상치(주인용 97.5·보조 56.0 등)와 일치했습니다. 각 DB의 접근 방식은 이용약관을 근거로 자동/사람으로 나눴습니다(2장). 실제 서버 호출·크롤링은 하지 않았습니다 — DB 문법·URL·한도는 바뀔 수 있으니 첫 사용 때 확인하세요. 법 조문·판단 기준은 개념 안내이며 최종 판단은 변리사가 합니다. 이 편은 유튜브 링크가 제공되지 않아 영상 자료는 쓰지 않았습니다.

01전체 흐름과 승인 관문

한 건의 조사를 ‘사건 폴더’ 하나로 관리하고, 중요한 지점마다 사람이 승인하는 관문(G)을 둡니다.

단계하는 일관문
1 접수청구항·우선일·목적 확인(빠진 건 하나만 질문)–
2 검색식 제안특징 분해 → 개념 조사식 → DB별 식·URLG1 조사식 승인
3 검색공식 API 자동, 웹 DB는 링크/식을 사람이 실행G2 호출량 승인
4 통합·선별패밀리 병합, 읽을 순서 결정–
5 구성대비특징별 ●/◐/○ + 근거 위치 기록–
6 산정점수·분류(A/B/C/X)·결합 경로G4 판정 검토
7 보고·보충후보·대비표·결합 경로·한계, 빈 특징만 재검색–
관문이 말뿐이 아니게 — 코드에 장치를 넣었습니다. ① API 명령은 dry-run이 없으면 예상 호출량만 보여 주고 실제 호출은 안 함, ② 사건별 예산을 넘으면 중단, ③ 근거 위치 없이 ●·◐를 적으면 산정이 실행되지 않음(사후고찰 방지).

02자동 vs 사람 실행 — 기술이 아니라 ‘약관’ 문제

웹 DB를 브라우저로 반복 조회하지 않는 이유는 기술적 한계가 아니라 이용 조건 때문입니다.

DB접근근거(요지)
KIPRIS PlusAPI 자동공식 오픈 API로 자동 검색·수집
EPO OPSAPI 자동로봇 조회는 Espacenet 웹이 아닌 OPS 같은 REST로 — 주당·속도 한도 있음
Google(BigQuery)대량은 API웹엔 공식 검색 API 없음. BigQuery는 처리량 과금 — dry run으로 사전 확인
PATENTSCOPE사람만WIPO 약관이 자동 질의 금지
Espacenet·Google 웹·KIPRIS 웹사람스킬이 식·URL을 만들고 사람이 실행, 결과 CSV를 저장
그래서 — KIPRIS Plus + EPO OPS + BigQuery 조합으로 1차 자동 조사를 하고, 웹 DB는 전문·다국어 확장·법적 상태 확인 같은 보완·검증 단계로 둡니다. 브라우저 자동화로 웹 DB를 반복 조회하는 것은 약관 위반이라 스킬 지침에 금지로 넣었습니다.

03개념 조사식 → DB별 변환

DB마다 검색식을 손으로 다시 쓰면 문법 오류가 나고 결과 비교가 어렵습니다. 그래서 개념 조사식 하나를 만들어 DB별 문법으로 자동 변환합니다.

개념KIPRISGoogle PatentsEspacenet/OPSPATENTSCOPE
AND / OR* / +AND / ORand / orAND / OR
근접^nNEAR/nprox/distance<nNEARn
필드TL=[] AB=[] CL=[]TI= AB= CL= TAC=ti= ab= ta=EN_TI: EN_AB: EN_CL:
날짜공개일 칸URL before=publication:pd<DP:[ TO ]
언어 전략 — KIPRIS(국내)는 한국어, 나머지는 영어로. Google·PATENTSCOPE는 기계번역 색인을 포함하므로 미국·영국식 철자와 단·복수를 모두 넣습니다. 자세한 문법 주의점(KIPRIS 근접의 단어 단위 한계, Google 괄호 안 NEAR, Espacenet 절단기호·내보내기 한도)은 db-syntax.md에.

04처음 접근과 바뀐 점

① “DB마다 검색식을 새로” → 개념 조사식 하나로 변환 — DB별로 손으로 다시 쓰면 문법 오류와 누락이 생깁니다. 개념 조사식(plan.json) 하나를 만들어 DB별로 자동 변환하면 같은 특징 조합을 모든 DB에 적용해 결과를 비교할 수 있습니다.
② “AI가 제일 비슷한 걸 골라줘” → 판단과 집계를 분리 — 한 번에 결론 내리면 근거 검증이 안 됩니다. 특징별 개시 여부를 근거 위치와 함께 기록하고(판단), 순위는 공개된 점수 규칙으로 계산합니다(집계). 그래야 재현·검토됩니다.
③ “웹 DB도 자동으로 긁자” → 약관상 사람이 실행 — PATENTSCOPE·Espacenet 웹 등은 자동 질의가 약관 위반입니다. 공식 API만 자동으로, 웹 DB는 식·URL을 만들어 사람이 실행합니다. 브라우저 자동화 반복 조회는 금지입니다.
④ “주인용은 하나로 확정” → 상위 2~3건을 각각 출발점으로 — 최근접 선행기술은 출발점이 여럿일 수 있습니다(EPO 실무). 하나로 고정하지 않고 상위 후보를 각각 출발점으로 검토해 진보성 논리를 비교합니다.
⑤ “개시율이 높으면 선행문헌” → 날짜가 먼저 — 공개일이 기준일(우선일) 이후면 개시율이 90%여도 선행문헌이 아닙니다(X). 다만 확대된 선출원·선출원은 기준일보다 늦게 공개돼도 해당할 수 있어, cutoff 없는 KR 검색을 따로 돌립니다(7장).
⑥ “근거는 나중에” → 근거 없으면 산정 중단 — 근거 위치 없이 ●·◐를 적으면 사후고찰(알고 나서 꿰맞추기)에 빠지기 쉽습니다. 도구가 근거 없는 판정을 발견하면 산정을 멈춰, 근거 기록을 강제합니다.

05검색식 생성 — 개념 하나로 네 DB(시범)

가상의 ‘수직 스크루 착즙기 — 드럼 내면 경사 리브’ 발명으로, build_queries.py가 개념 조사식을 DB별로 변환했습니다.

$ python tools/build_queries.py sample/plan.json --sheet work/search_sheet.md

## KIPRIS
- Q2 (F1*F2*F3 핵심 조합)
  식: TL=[(스크루+스크류)*(리브+돌기)*(착즙+주스+녹즙)]        ← 한국어·* = AND

## GooglePatents
- Q2
  식: TAC=((screw OR auger) AND (rib OR protrusion) AND (juicer OR juice extractor))
  열기: https://patents.google.com/?q=...&before=publication:20200315   ← 기준일 자동 한정
무엇을 배우나 — 특징(F1·F2·F3)의 한/영 키워드를 각 DB 문법으로 바꾸고, 신규성용은 기준일 이전으로 자동 한정합니다. KR은 확대선출원 검토용으로 cutoff 없는 식도 함께 만들고, 웹 DB는 링크와 식 원문을 같이 적어 링크가 안 열려도 붙여넣을 수 있게 합니다. (전체: search_sheet.md)

06최근접 산정 — 판단을 규칙으로(시범)

구성대비 결과(mapping.json, 특징별 ●/◐/○ + 근거)를 rank_closest.py가 같은 규칙으로 집계했습니다.

$ python tools/rank_closest.py sample/plan.json sample/mapping.json

| 순위 | 문헌        | 분류             | 점수 | F1 | F2 | F3 |
| 1   | US9000002B2 | B 주인용발명 후보  | 97.5 | ◐  | ●  | ●  |
| 2   | KR100000001B1| C 보조 문헌      | 56.0 | ●  | ○  | ●  |
| 3   | CN100000003A | -               | 32.5 | ○  | ◐  | ○  |
| 4   | EP3000004A1  | X 기준일 이후 공개 |  –  | ●  | ●  | ◐  |

주인용 후보 US9000002B2 — 부족 특징 F1(◐) → KR100000001B1로 보완 가능
무엇을 배우나 — 핵심 특징 F2(가중치 3)를 ●로 개시한 US…02가 1위 주인용 후보가 되고, 그 부족 특징 F1을 ●로 개시한 KR…01이 보조 문헌(결합 경로)으로 자동 연결됩니다. EP…04는 개시율이 높아도 공개일이 기준일 이후라 X로 빠집니다. 점수(100×관련성×(1−수정부담/총가중치))는 판단의 집계일 뿐 법적 결론이 아니며, 효과의 현저성·청구항 해석은 따로 검토합니다. (보고서: closest_report.md)

07날짜 기준과 법 — 왜 두 번 검색하나

같은 조사식이라도 ‘날짜 조건’이 법적 성격을 가릅니다.

목적날짜 조건이유
신규성·진보성 선행기술공개일 < 기준일(우선일)기준일 이전 공개만 선행기술
확대된 선출원(제29조 제3항)·선출원(제36조)기준일 이후 공개도 포함(cutoff 없는 KR 검색)먼저 출원됐으나 나중에 공개된 선출원이 해당할 수 있음
핵심 — 그래서 KR은 ‘기준일 이전’ 식과 ‘기준일 제한 없는’ 식을 따로 돌립니다. 산정 도구도 기준일 이후 공개 문헌을 X로 분류하되 확대된 선출원 검토 대상으로 따로 표시합니다. 법 조문·판단은 개념 안내이며, 적용·최종 판단은 변리사가 사건별로 합니다. 판단 기준의 근거(EPO·한국 심사기준)는 selection-criteria.md에.

08활용과 주의할 점

조사식 설계·구성대비 같은 ‘판단 보조’는 어느 AI에서도 되지만, 실제 검색·전문 확보는 각 DB 약관을 따릅니다. Antigravity에는 사건 폴더 뼈대 작성을 맡기고 조사·판단은 변리사가 합니다.

상황이렇게
DB별 식 새로 쓰기개념 조사식 하나로 자동 변환해 결과 비교.
웹 DB 자동 수집약관 위반. 공식 API만 자동, 웹은 사람이 실행.
AI가 한 번에 결론판단(근거)과 집계(규칙) 분리. 근거 없으면 산정 중단.
주인용 하나로 확정상위 2~3건을 각각 출발점으로 검토.
날짜 간과신규성은 기준일 이전. 확대선출원은 cutoff 없는 KR도.
전문 대비 과다문헌당 분량이 크니 상위 10~15건으로 제한.
API 호출·처리량먼저 dry-run으로 확인 후 실행(예산 초과 시 중단).
최종 판단신규성·진보성·FTO는 변리사가. AI는 1차 초안.
