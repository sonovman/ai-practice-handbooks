바이브 코딩을 위한 Git·GitHub — 안전하게 공유하고 함께 고치기

바이브 코딩으로 나만의 스킬·에이전트를 만들고 나면 “이걸 팀원과 어떻게 같이 쓰지?”라는 물음이 따라옵니다. 폴더를 압축해 주고받는 방식은 파일이 많거나, 비밀 키가 섞여 있거나, 변경 이력을 남겨야 할 때 금세 한계에 부딪힙니다. 이 편은 비개발자도 Git·GitHub의 기본 개념과 내부 동작을 이해하고, 무엇보다 개인정보·비밀정보가 올라가지 않도록 ‘미리’ 막는 법을 중심으로 안전하게 공유·협업하는 법을 단계별로 다룹니다.

독자바이브 코딩·에이전트·스킬을 만들어 공유하고 함께 고도화하려는 비개발자, Git을 처음 쓰는 사람 분량읽기 약 30분 · 첫 공유까지 약 20분 · 템플릿(비밀정보 점검 도구 · .gitignore·pre-commit 훅 · 스킬 · 프롬프트 5종 · 시범) 판1.0 · 2026. 11. 8.
한 줄 결론

올리기 전에 막는 것이 가장 쉽고 안전합니다 — 비밀은 코드에서 분리하고, 올리기 전에 점검하고, 그래도 올라갔다면 즉시 폐기·재발급합니다.

Git의 커밋은 ‘스냅샷’이라 한 번 올라간 비밀은 파일을 지워도 과거 이력에 남습니다(7장 시범에서 실제로 보입니다). 그래서 사후 삭제보다 사전 차단이 핵심입니다. GitHub도 공개 저장소에는 비밀이 올라가는 것을 기본으로 막아 주지만, 그 앞단에서 내 손으로 한 번 더 거릅니다.

무엇을 확인했나 — 비밀정보 점검 도구는 시험 11개로 동작을 확인했고, 4·8장 시범은 일부러 가짜 키를 심은 폴더와 실제 git 저장소를 작성 환경에서 직접 돌린 결과입니다(가짜 값만 사용). GitHub Push protection·Secret scanning, git filter-repo 등 최신 사실은 공식 문서로 확인했습니다(부록).

01Git과 GitHub, 무엇이 다른가

GitGitHub
한 줄내 컴퓨터에서 변경 이력을 관리하는 프로그램그 저장소를 인터넷에 두고 함께 쓰는 창고·협업 공간
어디에로컬(내 PC)원격(웹)
역할커밋·브랜치로 이력·버전 관리공유·백업·리뷰(PR)·권한·자동화

구글 드라이브·드롭박스와 다른 점이 세 가지입니다. ① 많은 파일을 빠르게 다룹니다(웹 프로젝트는 파일이 수천~수만 개). ② API 키·결제 정보가 섞여 공유되는 사고를 구조적으로 막을 수 있습니다. ③ 변경 이력이 남아 언제든 되돌리고, 브랜치로 안전하게 나눠 협업합니다. 특히 바이브 코딩에서는 ②가 중요합니다 — 에이전트에 연결한 내 키가 실수로 공유되면 남이 쓸 때마다 내 요금이 나갑니다.

02내부 동작 — 스냅샷·커밋·브랜치

명령을 외우기 전에, Git이 무엇을 저장하는지 알면 사고를 피할 수 있습니다. 문서를 결재받아 보관하는 과정에 빗대 봅니다.

작업파일 수정 (작업 폴더)

준비스테이징 (Staging)

이번 커밋에 넣을 것만 추림

git commit — 도장 찍기
기록커밋 = 스냅샷 (영구 이력)

git push — 창고로
공유원격 저장소 (GitHub)

팀원과 공유·백업

  • 커밋은 스냅샷 — 그 시점의 파일 전체를 사진처럼 저장합니다. 그래서 과거로 되돌릴 수 있지만, 한 번 커밋된 비밀은 나중에 파일을 지워도 과거 스냅샷에 남습니다(8장).
  • 스테이징 — 수정한 것 중 이번에 올릴 것만 골라 담는 중간 단계. 변경을 주제별로 나눠 커밋할 수 있습니다.
  • 브랜치 — main(안정 버전)은 그대로 두고 복사본에서 작업하는 평행 세계. 실수해도 원본에 영향이 없습니다(6장).

03처음 접근과 바뀐 점

① “폴더를 압축해서 전달” → Git·GitHub — 가장 쉬워 보이지만, 파일이 많으면 느리고, 비밀 키가 섞여 통째로 넘어가며, 누가 무엇을 언제 바꿨는지 알 수 없습니다. Git은 변경 이력을 남기고, GitHub는 그 이력을 안전하게 공유·리뷰하게 해 줍니다. 압축 공유는 이 편에서 권하지 않습니다.
② “.gitignore에 넣으면 비밀이 안전” → .gitignore는 ‘파일 전체’만 막는다 — .env 같은 파일을 통째로 제외하는 데는 .gitignore가 맞습니다. 그러나 코드 안에 직접 적은(하드코딩) 키는 그 파일이 추적 대상이라 .gitignore로 막지 못합니다. 4장 시범에서 .env는 제외돼 경고로 내려갔지만 app.py에 박힌 키는 여전히 ‘실패’로 남습니다. 그래서 비밀은 코드에서 분리(환경 변수·.env)하는 것이 먼저입니다.
③ “올라갔으면 파일만 지우면 됨” → 이력에 남는다 — 비밀이 든 파일을 지우고 새로 커밋해도, 과거 커밋 스냅샷에는 그대로 남습니다(8장에서 실제 확인). 그래서 순서가 바뀌었습니다: ① 키를 먼저 폐기·재발급(올라간 순간 수집됐다고 가정) → 그다음 이력 제거. 사후 대응은 비싸고 불완전하므로 ‘올리기 전 점검’이 핵심입니다.
④ “내가 다 점검” → 사람과 도구와 GitHub 3겹 — 눈으로만 보면 놓칩니다. 이 편은 ① 올리기 전 로컬 점검 도구(secret_scan.py) ② 매 커밋 전 자동 점검(pre-commit 훅) ③ GitHub의 Push protection(공개 저장소는 비밀 포함 푸시를 기본으로 차단)을 겹칩니다. 어느 하나가 놓쳐도 다음이 받칩니다.
⑤ “터미널 명령을 외워야” → 말로 시키되 개념은 안다 — 클로드 코드 같은 에이전트에 “깃허브에 올려 줘”라고 말로 시키면 init→add→commit→push를 대신 해 줍니다. 편하지만, 무엇이 올라가는지는 사람이 알아야 사고를 막습니다. 그래서 명령을 자동화하되 커밋·푸시 전 점검을 습관으로 두고, 저장소를 바꾸는 동작은 승인 후 실행하게 했습니다. 선생님처럼 GitHub Desktop을 쓰면 끌어 올리기로 빠지기 쉬운 숨김 파일(.agents 등)도 함께 올라갑니다.
⑥ “main에 바로 올리면 빠름” → 혼자면 OK, 함께면 브랜치·PR — 혼자 쓰는 저장소는 main에 바로 커밋해도 됩니다. 그러나 여럿이 같은 저장소를 고치면 충돌과 사고가 납니다. 이럴 때 브랜치로 나눠 작업하고 PR로 합치며, main 보호 규칙으로 실수를 막습니다(6·7장). 규모에 맞게 고르면 됩니다.
⑦ “자동 테스트에 키를 넣어야” → GitHub Secrets로 주입 — CI 자동 검사에서 API 키가 필요할 때 YML이나 코드에 키를 적으면 또 유출입니다. GitHub의 Secrets에 키를 넣어 두고 실행 순간에만 환경 변수로 주입하면, 코드·이력에 남지 않고 로그에도 가려집니다(7장).

04올리기 전 비밀정보 사전 차단 (핵심)

올리기 전 세 가지를 점검합니다: ① 코드·설정에 든 비밀 값 ② 민감 파일 ③ 그 민감 파일이 .gitignore로 제외됐는지.

터미널 (추가 설치 없음)
python tools/secret_scan.py .                         # 현재 폴더 점검
python tools/secret_scan.py . --report work/secret.md  # 보고서로 저장
python tools/secret_scan.py --suggest-gitignore > .gitignore   # 추천 .gitignore 생성
# 종료 코드 0 이상없음 · 1 경고 · 2 실패(올리기 전 조치)

시범 — 가짜 키를 심은 폴더

일부러 키를 섞은 폴더(app.py에 하드코딩, .env, config.json)를 점검했습니다.

상태결과
.gitignore 없이실패 — .env(민감 파일 + 키), app.py의 OpenAI 키·DB 접속정보, config.json 비밀번호 모두 적발 (보고서)
.gitignore 추가 후여전히 실패 — .env는 제외돼 ‘경고’로 내려갔지만, app.py·config.json에 코드로 박힌 비밀은 그대로 ‘실패’ (보고서)

이 대비가 2장 ②의 핵심입니다. .gitignore는 파일 전체만 빼 줄 뿐, 코드에 박힌 비밀은 환경 변수로 옮겨야 사라집니다. 값은 가려서(sk-pro…op) 보여 줍니다.

습관으로 만들기 — 매 커밋 때 자동으로 점검하려면 pre-commit.sample을 저장소의 .git/hooks/pre-commit으로 복사하고 실행 권한을 줍니다. 비밀이 발견되면 커밋이 멈춥니다. 비밀은 코드가 아니라 환경 변수나 .env(제외됨)에 두고, 공유용으로는 빈 양식 .env.example만 올립니다.

05올리기 (init → commit → push)

GitHub Desktop (초보자 권장)

  1. 점검 먼저4장 점검을 통과했는지 확인합니다.
  2. 저장소 추가File → Add Local Repository로 폴더를 열거나, 새로 만들면 .git이 생깁니다.
  3. 변경 확인왼쪽 목록에서 올라갈 파일을 봅니다. 여기서 .env·키 파일이 보이면 멈추고 .gitignore에 추가합니다.
  4. 커밋Summary에 한 일을 적고 Commit to main.
  5. 공개 범위·올리기Publish repository에서 Private(비공개)를 기본으로 고르고 Publish. 이후 변경은 Push origin.

끌어 올리기(웹 Upload)는 점(.)으로 시작하는 폴더(.agents 등)를 건너뛰므로, 숨김 파일이 있는 바이브 코딩 프로젝트는 GitHub Desktop이 확실합니다.

에이전트에게 말로

클로드 코드 등
이 폴더를 깃허브에 올리기 전에 먼저 비밀정보를 점검해 줘(실패가 있으면 멈추고 알려줘).
통과하면 저장소 이름과 공개 범위(Private 권장)를 물어본 뒤, git init → add → commit → push 를 해 주고
완료되면 저장소 주소를 알려줘. 커밋 메시지는 내가 한 작업을 요약해 줘.

말로 시켜도 무엇이 올라가는지는 사람이 확인합니다. 명령으로 직접 하려면: git init → (점검 후) git add . → git commit -m "..." → 원격 연결 → git push.

06받아오기·협업 (pull · PR)

받아오기

  • clone — 저장소를 처음 통째로 내려받기. pull — 남이 올린 최신 변경만 가져와 합치기.
  • 협업 루틴 — 작업 시작 전 git pull → 작업 → 커밋 → git push. 시작 전에 당겨 오면 충돌이 크게 줄어듭니다.
  • 충돌(merge conflict) — 같은 줄을 둘이 고치면 생깁니다. 당황 말고 git merge --abort로 되돌리거나, 충돌 표시(<<<<)된 부분에서 양쪽을 합칩니다. 에이전트에게 “충돌난 부분을 안전하게 합쳐 줘”라고 맡길 수도 있습니다.

여럿이 — 브랜치와 PR 6단계

  1. 브랜치 생성git checkout -b feature/login — main은 두고 복사본에서 작업.
  2. 커밋기능 단위로 git add . → git commit -m "로그인 기능".
  3. 푸시git push origin feature/login.
  4. PR 생성GitHub에서 Compare & pull request → 제목·설명 작성 → Create.
  5. 리뷰팀원이 라인별로 검토·피드백. 수정은 같은 브랜치에 다시 커밋·푸시하면 PR에 자동 반영.
  6. 병합승인되면 Merge → 모두 git checkout main → git pull로 최신화.

07main 보호와 자동 검사

장치어디서효과
브랜치 보호 규칙저장소 Settings → Branches(또는 Rules) → main 지정PR 필수·리뷰 승인·상태 검사 통과를 켜면 main에 직접 푸시 차단. 관리자도 포함 가능
GitHub Actions (CI).github/workflows/ci.ymlPR이 올라오면 가상 서버에서 테스트·검사를 자동 실행. 통과해야 Merge 활성화
GitHub SecretsSettings → Secrets and variables → ActionsAPI 키를 코드가 아닌 보안함에 두고 실행 순간에만 환경 변수로 주입. 로그에도 ***로 가려짐
Secret scanning / Push protectionSettings → Security (공개 저장소는 기본 켜짐)비밀이 든 푸시를 GitHub가 받기 전에 차단. 내 점검의 마지막 안전망

브랜치 보호를 켜면 터미널에서 실수로 git push origin main을 해도 protected branch hook declined로 튕깁니다. CI 설정 YML은 에이전트에게 “우리 프로젝트에 맞는 GitHub Actions 테스트 YML을 .github/workflows/ci.yml에 만들어 줘”라고 맡기면 됩니다. 비밀 주입도 “Secrets의 OPENAI_API_KEY를 CI에서 환경 변수로 받도록 YML을 고쳐 줘”처럼 요청합니다.

== 그러나 과거 커밋 이력에는 키가 그대로 남아 있다
-API_KEY=sk-proj-FAKEdemo1234567890ABCDEF   ← 과거 커밋에 그대로
  1. 먼저 폐기·재발급제공자(OpenAI·Anthropic·AWS 등)에서 그 키를 즉시 삭제하고 새로 발급합니다. 올라간 순간 자동 수집됐다고 가정합니다. 이력 삭제보다 이게 1순위입니다.
  2. 이력에서 제거pip install git-filter-repo → git filter-repo --invert-paths --path .env(파일 통째) 또는 특정 문자열만 --replace-text. BFG도 대안입니다. (과거의 느린 filter-branch 대신 filter-repo가 현재 권장.)
  3. 강제 푸시git push origin main --force로 깨끗한 이력으로 덮습니다(커밋 해시가 모두 바뀜).
  4. 팀원 재클론이력이 바뀌었으니 팀원은 기존 폴더를 지우고 git clone으로 새로 받습니다.
  5. 재발 방지.gitignore 등록 · 코드에서 환경 변수로 분리 · GitHub Secret scanning/Push protection 확인.
주의 — 이력 재작성은 되돌리기 어렵습니다. 중요한 저장소라면 먼저 백업하고, 자신 없으면 동료·전문가와 함께 진행하세요. 에이전트에게 맡길 때도 “실행 전에 무엇을 할지 먼저 설명해 줘”라고 요청합니다.

09Antigravity·여러 AI 도구 (선택)

Git·GitHub는 도구를 가리지 않습니다. 작업 폴더에 점검 도구와 규칙을 두면 어느 에이전트에서나 ‘올리기 전 점검’을 습관화할 수 있습니다.

환경쓰는 법
Google Antigravity (16편)템플릿 starter를 열면 AGENTS.md·no-secrets 규칙·git-share 스킬이 적용됩니다. “올리기 전 점검하고, 통과하면 커밋·푸시해 줘”처럼 맡기면 secret_scan부터 돌립니다. git은 Antigravity의 터미널/에이전트가 실행.
Claude Code · Codex · Gemini CLI · GitHub Copilot CLI로컬 git을 말로 통제. git-share 스킬을 .claude/skills/ 등에 두면 같은 절차. 커밋·푸시 전 secret_scan.
Claude.ai · ChatGPT · Gemini 앱 · Copilot Cowork (웹)웹 앱은 내 PC의 git을 직접 실행하지 못합니다. git-share 스킬을 올려 두면 명령·절차·PR 설명 작성을 돕는 조언자로 쓰고, 실제 실행은 GitHub Desktop이나 CLI에서 합니다.

업로드용 스킬 묶음은 템플릿 upload/에 있습니다. 어느 도구든 “비밀값은 가려서, 올리기 전 점검”이라는 규칙은 같습니다.

10주의할 점

상황주의할 점
.gitignore 믿기파일 전체만 제외합니다. 코드에 박힌 키는 환경 변수로 옮겨야 사라집니다.
파일만 지우기과거 커밋 이력에 남습니다. 먼저 키를 폐기·재발급하고 이력을 제거합니다.
점검 도구 맹신100% 탐지는 없습니다. 도구·pre-commit·GitHub·사람의 눈을 겹칩니다.
공개 범위민감하면 Private. 사내 자료·고객 정보·영업비밀이 섞였는지 확인합니다.
main 직접 푸시여럿이면 브랜치→PR. 브랜치 보호로 실수를 막습니다.
강제 푸시·이력 재작성되돌리기 어렵습니다. 백업하고, 팀원에게 재클론을 알립니다.
CI에 키 적기YML·코드에 키 금지. GitHub Secrets로 주입합니다.
개인 서버 경유 공유불명의 중계 서버로 코드를 주고받지 않습니다. 공식 GitHub·GitHub Desktop·로컬 git을 씁니다.
끌어 올리기숨김 파일(.agents 등)이 빠집니다. GitHub Desktop을 권합니다.
비밀값 출력에이전트에게도 전체 값을 보여 주지 말라고(가려서) 요청합니다.
