핸드북 15 · 특허

텍스트 쌍 특허 분석을 범용 LLM에서 — 유사 특허 판별과 FTO

청구항은 그 특허의 발명의 설명으로 해석해야 한다는 원칙을 기계 학습의 구조로 바꾼 것이 특허출원 10-2024-0075102(공개 10-2025-0013094)의 아이디어입니다. 청구항과 발명의 설명을 짝지은 ‘텍스트 쌍’을 판단 단위로 삼고, 같은 문헌에서 나온 쌍과 다른 문헌에서 나온 쌍을 자동으로 구별해 학습합니다. 이 편은 그 아이디어를 Claude·ChatGPT·Gemini·Microsoft 365 Copilot 같은 범용 LLM에서 유사 특허 판별과 FTO(Freedom to Operate) 분석에 쓰는 방법을 설계하고, 전처리·클레임 차트·점검 도구와 함께 시범을 보입니다.

독자변리사·특허 담당자, 연구소의 IP 담당, 특허 분석 도구를 만드는 개발자 분량읽기 약 30분 · 템플릿(스킬 · 전처리·점검 도구 · 미세 조정 참고 코드 · 시범 자료 · 플랫폼 설정) 판1.0 · 2026. 11. 7.
한 줄 결론

자르고 찾는 일은 도구가, 구성요소별 판단과 근거 인용은 LLM이, 대량 선별 점수는 내가 소유한 작은 모델이, 결론은 변리사가.

출원발명의 세 부분 — 입력 자동 전처리, 자동 레이블과 교대 학습, 유사·침해 판단 — 은 범용 LLM 시대에도 그대로 살아납니다. 다만 역할이 바뀝니다. LLM은 512토큰 한계에서 벗어나 구성요소 단위로 근거를 인용하는 판단자가 되고, 자동 레이블 규칙은 대조군·평가 세트·소형 모델 학습 데이터를 공짜로 만들어 주는 장치가 됩니다.

01출원발명의 핵심

전처리

청구항과 설명을 짝짓기

식별 태그로 청구범위(제1 텍스트)와 발명의 설명(제2 텍스트)을 자동 추출. 독립항 중심, 설명은 조각으로 나눠 청구항 벡터와 유사도가 높은 조각을 고름 (청구항 1~4).

학습

자동 레이블 + 교대 학습

같은 문헌 쌍 = 제1 레이블, 다른 문헌 쌍 = 제2 레이블. 사전 학습 언어모델 + 분류 층을 두 그룹을 번갈아 넣어 손실 평균으로 학습 (청구항 5~8).

판단

유사·특허성·침해

관심 특허 청구항 × 대상 특허 설명 → 특허성, 관심 특허 청구항 × 제품 기술 설명서 → 침해 여부 (청구항 9~11).

실험 항목내용 (명세서 실험예)
데이터관심 특허(미국 등록 A, 설명 약 4,700단어·청구항 약 340단어), 비교 특허(B, 범위 밖), 시험 특허(C, 범위 안·다른 용어)
전처리청구항 핵심 특징을 약 190토큰 한 문장으로 요약, 설명은 310토큰 조각, 벡터 유사도로 잡음 제거 → 각 17쌍
학습Hugging Face BertForSequenceClassification, label 1·0 데이터로더를 zip으로 번갈아, 두 손실 평균
결과15 에포크에 정확도 약 80%. 다른 용어로 쓴 시험 특허 C의 17쌍이 모두 label 1로 예측
실험 규모를 읽는 법 — 이 실험은 관심 특허 1건을 중심으로 한 개념 증명입니다. 같은 사상을 다른 말로 쓴 문서를 잡아냈다는 점에서 방향을 보여 주지만, 다른 분야·다른 청구항에도 같은 성능이 나온다는 뜻은 아닙니다. 그래서 범용 모델로 넓힐 때는 같은 자동 레이블 규칙으로 평가 세트를 먼저 만들고(8장), 학습과 검증을 특허 단위로 나눠 같은 특허의 문장이 양쪽에 섞이지 않게 해서 성능을 다시 잽니다.

03옮기면서 다듬은 여섯 곳

① 레이블의 이름 — “유사/침해”에서 “개시(지지) 관계”로 — 처음 설계에서는 같은 문헌 쌍을 “유사·침해(1)”, 다른 문헌 쌍을 “비유사·비침해(0)”로 불렀습니다. 학습 목표를 직관적으로 보여 주는 이름입니다. 그런데 같은 문헌 쌍이 실제로 가르쳐 주는 것은 “이 설명이 이 청구항을 뒷받침한다”는 개시·지지 관계이고, 침해는 여기에 청구항 해석, 균등, 실제 실시 사실이 더해지는 법률 판단입니다. 범용 LLM으로 옮기면서 판단의 이름을 “구성요소가 대상 문서에 개시되었는가”로 좁히고, 침해·무효 결론은 차트를 본 변리사가 내리도록 나눴습니다.
② 청구항 요약 → 구성요소 분설 — BERT의 512토큰 안에 설명이 들어갈 자리를 만들려고 청구항을 약 190토큰 한 문장으로 줄였습니다. 당시 구조에서는 합리적인 선택입니다. 하지만 요약은 어떤 한정 요소를 빼먹을 수 있고, 특허 판단은 모든 구성요소를 하나씩 확인해야 합니다. LLM은 긴 입력을 받을 수 있으므로 요약 대신 전제부 + E1…En으로 분설하고 청구항 문언을 그대로 둡니다.
③ 문서 단위 이진 판정 → 구성요소 단위 판단과 결론 규칙 — 실험에서는 설명 조각 17개가 각각 1인지 0인지를 보았습니다. 범용 LLM에서는 판단 단위를 한 단계 더 쪼개, 구성요소마다 개시 여부를 원문 인용과 함께 정하고, 결론은 “구성요소별로는 어느 조각에서든 개시되면 개시(최대), 청구항 전체는 모든 구성요소가 개시되어야 개시(최소)”라는 규칙으로 냅니다. 조각 다수결로는 한 구성요소가 빠진 경우를 놓칠 수 있기 때문입니다. chart_check verify가 이 규칙과 결론이 맞는지 기계적으로 확인합니다.
④ 512토큰 필터 → 근거 위치를 찾는 필터 — LLM의 입력 한계가 넉넉해지면 설명을 거를 필요가 없어 보입니다. 짧은 문서는 실제로 전문을 넣습니다. 그러나 수백 쪽 명세서나 여러 문서를 비교할 때는 여전히 걸러야 하고, 무엇보다 “어느 문단이 근거인가”를 특정해야 차트가 됩니다. 그래서 필터의 목적을 “길이 맞추기”에서 “구성요소별 근거 후보 찾기”로 바꿔 유지했습니다. 글자 유사도는 후보를 좁히는 데만 쓰고, 다른 용어로 쓴 문서는 점수가 낮게 나오므로 판단 근거로 쓰지 않습니다(6장 시범에서 실제로 0.05~0.17).
⑤ 무작위 음성 → 어려운 음성, 그리고 거짓 음성 경계 — 다른 문헌 쌍을 무작위로 고르면 대부분 분야부터 달라 너무 쉬운 문제가 됩니다. 평가와 학습에는 가장 비슷한 다른 문헌(같은 분류코드·같은 기술)을 함께 넣어야 실력이 드러납니다. 다만 비슷한 다른 문헌 중에는 같은 패밀리, 분할·계속 출원, 서로 인용한 문헌처럼 실제로는 개시 관계가 있는 것이 섞입니다. pairs는 어려운 음성에 유사도를 표시하고, 학습 전에 눈으로 확인하라고 알려 줍니다.
⑥ “프로젝트로 파인튜닝” → 맥락 특화와 가중치 학습을 나누기 — Claude·ChatGPT 프로젝트, Gemini 스킬, Copilot 에이전트에 분야 자료를 넣으면 그 분야에 맞춰진 것처럼 동작합니다. 이것은 모델의 가중치를 바꾸는 미세 조정이 아니라 매번 참고 자료와 지침을 함께 넣는 맥락 특화입니다. 분야별 용어집·지난 차트 예시·판단 기준을 프로젝트에 쌓는 것은 효과가 크고 바로 할 수 있지만, “학습시켰다”고 이해하면 자료를 빼는 순간 성능이 돌아간다는 점을 놓칩니다. 가중치 학습이 필요한 부분(대량 선별 점수)은 8장의 소형 모델로 따로 합니다.

06시범 — 내 출원 청구항으로 FTO

관심 특허는 작성자의 공개 출원 KR 10-2025-0013094 청구항 1입니다. 대상 문서는 연습용으로 지어낸 두 제품 설명서입니다 — 출원발명과 같은 방식으로 학습 데이터를 만드는 「ClaimMatch Pro」, 키워드 검색 도구 「KeywordScout」. 모든 파일은 템플릿의 sample/에 있습니다.

① 분설 (pairkit elements)

청구항 1 — 분설 초안
전제부: 독립변수인 텍스트 쌍 및 이에 지정된 종속변수인 레이블을 포함하는 학습 데이터를 생성하는 컴퓨팅 장치에 의해 수행되는 방법으로서
E1 복수의 특허문서의 제1 항목으로부터 각 특허문서에 대한 제1 텍스트 시퀀스를 추출하고, 상기 복수의 특허문서의 제2 항목으로부터 각 특허문서에 대한 제2 텍스트 시퀀스를 추출하는
E2 상기 제1 텍스트 시퀀스와 상기 제2 텍스트 시퀀스를 결합하여 텍스트 쌍(text pair)을 생성하는
E3 상기 텍스트 쌍에 대해 발명의 유사 여부에 관한 레이블을 지정
E4 상기 학습 데이터는, 동일한 특허문서에서 추출된 … 텍스트 쌍으로 이루어진 제1 그룹
E5 서로 다른 특허문서에서 추출된 … 텍스트 쌍으로 이루어진 제2 그룹
E6 상기 제1 그룹에 속하는 텍스트 쌍에는 제1 레이블이 지정되고, 상기 제2 그룹에 … 제2 레이블이 지정되는

② 요청문 (pairkit bundle) → ③ 스킬의 차트

요청문에는 구성요소, 관심 특허 자신의 설명에서 찾은 용어 해석 근거(예: E3 ← [0083] “각 텍스트 쌍에 대해 발명의 유사 여부에 관한 레이블을 지정한다”), 대상 문서 전문이 들어갑니다. 글자 유사도는 「ClaimMatch Pro」도 0.05~0.17로 낮았습니다 — 같은 내용을 “정답값”, “공보”, “입력 샘플” 같은 다른 말로 썼기 때문이고, 이 차이를 메우는 것이 LLM의 몫입니다.

구성요소「ClaimMatch Pro」「KeywordScout」
E1 청구범위·설명 추출개시 [0002] “청구항 본문과 … 상세한 설명 본문을 각각 분리하여 저장”부분 개시 [0002] 청구항만 색인
E2 텍스트 쌍 생성개시 [0003] “이어 붙여 하나의 입력 샘플로”미개시
E3 유사 여부 레이블개시 [0004] “정답값 1(관련 있음)” — 관심 특허 [0083]의 뜻으로 해석부분 개시 [0003] 사람이 문헌에 다는 ‘관련/무관’ 표시
E4~E6 동일/다른 문헌 그룹과 레이블개시 [0004] “같은 공보… 1”, “서로 다른 공보… 0”미개시
결론모든 구성요소 개시 → 문서 기준 침해 위험 높음일부 미개시 → 청구항 1 범위 밖

④ 인용 점검 — 지어낸 근거를 잡아내기

정상 차트 두 개는 실패 0건으로 통과했습니다. 비교를 위해 일부러 흠을 넣은 첫 초안(chart-A-draft.md)을 점검하면 다음과 같이 걸러집니다.

[실패] 구성요소   빠짐: E6
[실패] E1     인용문을 원문에서 찾지 못했습니다(최고 일치 75%) — 지어냈거나 중간을 생략·바꿔 쓴 인용
[실패] E2     인용문을 원문에서 찾지 못했습니다(최고 일치 38%) — 지어냈거나 중간을 생략·바꿔 쓴 인용
[주의] E3     균등 검토 필요 — 사람이 판단
[주의] E4     인용문은 [0004]에 있습니다(표시는 [0005]).
[통과] E5     개시 · 인용 확인 [0004]
[실패] 결론     '모든 구성요소 개시' → 모든 구성요소 원칙상 '추가 검토 필요'

E1은 원문 중간(“<claims> 태그 안의”)을 생략한 인용이라, E2는 원문에 없는 문장이라 실패합니다. 결론은 E3이 ‘불명’인데 ‘모두 개시’라고 앞서 썼기 때문에 실패합니다.

관심 특허와 지어낸 짧은 특허 4건(커피 추출·배터리 열관리·문서 요약·특허 검색)으로 15쌍을 만들고, Claude가 쌍마다 “설명이 청구항을 개시하는가”를 판정한 결과입니다.

미세 조정을 어디에 둘 것인가 — 처음에는 “분야별로 대형 LLM을 파인튜닝한다”는 그림이 자연스럽습니다. 그러나 대형 모델의 미세 조정 창구는 열렸다 닫히기를 반복하고, 학습한 모델은 기반 모델이 내려가면 함께 사라집니다. 그래서 가중치 학습은 내가 소유할 수 있는 소형 모델(대량 선별 점수)에 두고, 대형 LLM은 맥락 특화(프로젝트·스킬·에이전트)로 정밀 판단과 설명을 맡기는 구성이 오래갑니다. 출원발명의 BERT 교차 인코더가 바로 그 소형 모델 자리에 들어갑니다.

참고 코드 (finetune/)

train_cross_encoder.py — 교대 배치 학습의 핵심
dl1 = DataLoader(label1_pairs, batch_size=8, shuffle=True, collate_fn=collate)   # 같은 문헌 쌍
dl2 = DataLoader(label0_pairs, batch_size=8, shuffle=True, collate_fn=collate)   # 다른 문헌 쌍
for epoch in range(15):
    for b1, b2 in zip(dl1, dl2):                          # 두 그룹을 번갈아
        loss = (model(**b1).loss + model(**b2).loss) / 2  # 두 손실의 평균
        loss.backward(); opt.step(); sched.step(); opt.zero_grad()
# 검증은 특허 단위로 분리 — 같은 특허의 문장이 학습·검증에 함께 들어가지 않게

train_embedding.py는 pairs --triplets의 (청구항, 같은 문헌 설명, 어려운 다른 문헌 설명)으로 임베딩 모델을 학습합니다. 한 배치 안의 다른 문헌이 모두 음성이 되는 손실(MultipleNegativesRankingLoss)이라 자동 레이블 규칙을 대량으로 쓰는 셈입니다. 두 파일은 참고 구현으로, 이 핸드북을 만든 환경에서는 모델 내려받기가 막혀 문법 검사까지만 했습니다. 내 PC나 Colab에서 pip install torch transformers sentence-transformers 후 실행하세요.

09주의할 점

상황주의할 점과 바로잡는 방법
LLM 차트를 그대로 의견서에 쓸 때차트는 1차 자료입니다. 인용 점검을 통과해도 해석의 옳고 그름은 변리사가 확인합니다.
미공개 제품 사양을 올릴 때영업비밀입니다. 학습에 쓰지 않는 업무용 요금제·사내 에이전트를 쓰거나, bundle로 필요한 문단만 보냅니다.
출원 중인 청구항으로 FTO를 볼 때등록 청구항은 달라질 수 있습니다. 공개 출원은 위험 감시용으로, 판단은 등록 청구항으로 다시 합니다.
제품 설명서만 보고 결론 낼 때문서와 실제 동작이 다를 수 있습니다. 차트에 “문서 기준”임을 적고 실물·소스 확인을 따로 합니다.
균등을 LLM에 맡길 때균등은 다섯 요건을 따지는 법률 판단입니다. 스킬은 후보만 표시하고 판단은 사람이 합니다.
글자 유사도로 결론 낼 때같은 뜻을 다른 말로 쓰면 점수가 낮습니다. 유사도는 후보 좁히기에만 씁니다.
어려운 음성을 그대로 학습할 때같은 패밀리·인용 문헌은 실제로 개시 관계일 수 있습니다. 유사도가 높은 음성은 눈으로 확인합니다.
학습·검증을 쌍 단위로 섞을 때같은 특허 문장이 양쪽에 들어가 점수가 부풀려집니다. 특허 단위로 나눕니다.
작은 평가 세트의 만점15쌍 만점은 우연·쉬운 문제일 수 있습니다. 같은 분야 수백 쌍으로 다시 잽니다.
